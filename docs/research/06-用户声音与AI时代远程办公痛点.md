# 06 · 用户声音与 AI 时代远程办公痛点

> 调研日期：2026-09-03 ｜ 面向产品：terminalX（多端远程操控 PC 上的 AI CLI 工具）
> 目标：收集 2025–2026 年开发者远程使用 Claude Code / Codex / 其他 AI CLI 的真实声音，按频率与严重度排序痛点，给出典型用户画像。

## 0. 调研方法与来源说明（先读）

- **一手来源（本次直接读取原文）**：GitHub issues / discussions（anthropics/claude-code、openai/codex、slopus/happy、anomalyco/opencode 等）、开源项目 README（Happy、VibeTunnel、Paseo、CloudCLI、cc-connect、VibeAround 等）、Claude Code 官方文档（Remote Control、Agent View、Common workflows）。
- **二手来源**：V2EX、知乎、少数派、腾讯云开发者等中文社区内容，本次环境下这些域名被代理拦截，相关条目引自本仓库 `03-AI编码代理远程控制方案.md` / `02-终端与SSH远程方案.md` 里的搜索摘要，正文一律标注「待核实」。
- **未能覆盖**：Reddit（r/ClaudeAI、r/ClaudeCode、r/codex）、Hacker News、X/Twitter、B 站、掘金——域名被拦截且搜索配额耗尽。GitHub issue 的评论区也无法读取（仅能读 issue 正文与 discussion 评论），因此「反应数（👍）」是本文衡量共鸣度的主要量化指标。
- 引文均为原文摘录（英文保留原文，中文原文保留中文），链接附在每条之后；数字（Star、👍、评论数）为 2026-09-03 抓取值。

## 1. 一句话结论

**2026 年的开发者已经把「走开」当成 AI CLI 的默认用法**——起一个任务、去开会 / 吃饭 / 睡觉，回来验收。但每一家官方遥控（Claude Remote Control、Codex Remote）都在同一批地方摔跤：**通知缺失、审批卡住、断线后静默失效、多会话没有总览、Windows 二等公民、绑定厂商账号与网络**。社区因此长出了 Happy（23.6k★）、Paseo（15.9k★）、cc-connect（15.3k★）、CloudCLI（13.6k★）这一批「第三方遥控器」，而它们又各自只解决一部分问题。这正是 terminalX 的空间。

## 4. AI 时代远程办公的新变化

1. **开发者的工作从「写代码」变成「监工」。** codex #37967 的表述最准确："The realistic loop is: keyboard + terminal on the workstation; phone as a second screen for status + decisions while away from the desk." 用户 @mattbidinger："for itops it keeps me working when I'm away from my desk"（#9200）。Anthropic 把这写进了产品文案：Agent View 是「dispatch and manage many Claude Code sessions from one screen」。
2. **并行是默认形态：git worktree + 多会话。** 官方 Common workflows 直接给出 `claude --worktree feature-auth`「Run the same command with a different name in a second terminal to start an isolated parallel session」；Remote Control 服务器模式提供 `--spawn worktree`；Grok Build「最多 8 个子代理跑在 git worktree」（见 04 报告）。用户的相应诉求是「Native Git Worktree Management for Parallel & Isolated Agent Execution」（#17774）、「Session state should persist across git worktrees」（#15776 👍47）。
3. **「一台电脑 20 个会话」不再是极端案例。** #77252 的用户在一台 Windows 10 上有约 20 个由定时任务每天早上自动拉起的会话，全靠手机巡视；#33979 记录了「468 个会话导致启动冻结」。会话管理（命名、分组、清理、杀进程）成为基础设施需求。
4. **遥控成了选型决定因素。** codex discussion #9200（190 票、46 人）里多位用户表示因 Claude 有 Remote Control 而不换 Codex："I'm still choosing to run most of my sessions on Claude Code because I can step away and carry on"（@RoyalWares，2026-07-19）；"If codex does not implement it soon, I am going back to Claude"（@shreshthsaini）。
5. **每家厂商都在复制同一模式，用户手里却有多个 CLI。** Claude Remote Control（2026-02）、Codex 手机遥控（2026-05）、Kimi/ZCode/MiniMax 的类似功能（见 03 报告）——全部绑自家账号与 relay。Paseo（15.9k★）"One interface for Claude Code, Codex, Copilot, OpenCode, and Pi agents" 与 VibeAround 的出现说明「工具无关」是社区共识。
6. **中国语境：IM 即遥控器。** cc-connect（15.3k★，飞书/钉钉/企微/微信/QQ）、cc-weixin、openclaw-china（4.0k★）——国内开发者习惯用聊天软件而非专用 App 收通知与回复审批，而且必须「无公网 IP」。

## 5. 三个典型用户画像（草案）

### 画像 A：「盯盘的独立开发者」——Windows 台式机 + 手机
- **背景**：一人公司 / 副业，家里一台 Windows 11 台式机常年开机，主力工具 Claude Code（Max 订阅或走中转站 API Key），偶尔 Codex / Kimi 比价。
- **典型一天**：早上起 3–5 个任务（多 worktree），出门；地铁上用手机看进度、批准几个 Bash；晚上回来验收合并。
- **原话映射**："I use Claude Code primarily from my phone via the Claude mobile app's Remote Control feature. Having to walk to my PC…"（#48949）；"Currently unusable on Windows"（happy #496）。
- **痛点 Top3**：Windows 上没有靠谱的被控端；断线后不知道；走中转站的 Key 用不了官方 Remote Control。
- **对 terminalX 的要求**：Windows 原生一键安装成服务、断线可见 + 自动拉起、任何 API 配置都能用、微信/飞书推送。

### 画像 B：「多机器多 agent 的监工型工程师」——公司 Mac/Linux + 家里 Windows + 云 VPS
- **背景**：资深工程师 / 技术负责人，同时管 2–4 台机器上 10–20 个会话（Claude Code + Codex + 子代理），用 tmux 或 Windows 服务保活，习惯 Tailscale + Termius。
- **原话映射**："~20 local sessions on one desktop… user monitors/steers them remotely from a phone"（#77252）；"across multiple OS targets… I access all the Claude sessions in remote control"（#9200）；"guess the session roulette"（#2112）。
- **痛点 Top3**：没有跨机器、跨工具的「谁在等我」总览；权限 / 审批在远程端不一致；用量看不见谁在烧。
- **对 terminalX 的要求**：一个 Web 页面里按机器 × 工具 × 会话分组，「Needs input」置顶；审批持久化、可批量；每会话 token / 额度面板；会话命名与清理。

### 画像 C：「团队 / 企业里的远程办公者」——安全与合规敏感
- **背景**：公司笔记本 + 家中工作站，公司有 ZDR / 数据出境要求或用 Bedrock / 网关；想让 agent 通宵跑但需审计。
- **原话映射**："Organizations with compliance requirements such as Zero Data Retention can't enable Remote Control"（官方文档）；"the user had no way to know their sessions were RC-bound"（#88875）；"Is this usage pattern covered by my Max plan?"（#31534）。
- **痛点 Top3**：官方遥控要把转录送到厂商云；默认开启 / 静默绑定不可接受；Bedrock / 网关用户直接被排除。
- **对 terminalX 的要求**：自建中转节点、端到端加密、明确的启停开关、操作审计日志、可选只读观察者。

## 6. 对 terminalX 的机会点（可借鉴设计）

1. **把「连接状态」做成一等公民**：被控端心跳 + 控制端显式 Disconnected 徽标 + 本机 watchdog 自动重连 / 重启（对应痛点 #1；参考 #34255 提出的 "heartbeat or status indicator"、#28571 的 "Detect / Prevent / Resync / Fall back"）。
2. **审批与提问是持久对象，不是弹窗**：跨端可见、不过期、继承本地权限模式、可批量放行（对应 #2/#5；反例：Remote Control 5 分钟 `dialogExpiry`、Happy 审批超时断连）。
3. **跨机器 × 跨工具的 Agent View**：借鉴官方 Agent View 的状态模型（Working / Needs input / Idle / Completed / Failed / Stopped，Needs input 置顶），但扩展到多台机器与 Claude / Codex / Kimi / MiniMax / Grok（对应 #3/#7）。
4. **Windows 原生被控端**：不依赖 WSL / Git Bash，用 ConPTY 提供真终端；以 Windows 服务运行并处理睡眠 / 重启 / 锁屏；避免 Desktop 那种 15 分钟 idle taskkill（对应 #4；参考 #68625、#91592）。
5. **终端 + 聊天双视图**：官方只有聊天视图（GeekNews / V2EX 抱怨），SSH 只有终端；terminalX 应同一会话既能看 xterm 真终端又能看结构化事件流与审批卡片（对应 #8）。
6. **通知按事件配置、多渠道投递**：permission_prompt / idle_prompt / agent_completed / error 分别配置，投递到微信 / 飞书 / 钉钉 / Telegram / ntfy / Web Push（对应 #2；参考 cc-connect 的 13 平台与「无公网 IP」）。
7. **用量面板**：每机器 / 每会话 / 每子代理的 token 与 5h / 7d 额度；额度耗尽自动等待并续跑（对应 #6；参考 #35744 与 statusLine JSON）。
8. **中转 API 友好 + 自建 relay**：任何 `ANTHROPIC_BASE_URL` / API Key / Bedrock 都能遥控（对应 #7）。
9. **安全可感知**：端到端加密、默认关闭、显式配对、审计日志、只读分享（对应 #10；Happy 的 E2E 与 Zellij 的只读 token 可借鉴）。
10. **会话管理基础设施**：命名、分组（按项目 / worktree）、跨机器接续（导出 / 导入或 relay 同步转录）、清理孤儿进程（对应 #3/#9；参考 #33979 的 `claude sessions` 设计稿）。
