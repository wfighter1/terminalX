# 03 · 「远程控制 AI 编码代理」赛道调研：官方方案、第三方方案与空白

> 调研日期：2026-09-03 ｜ 面向：terminalX 第一阶段（Web 页面控制 Windows 电脑上的终端 + AI CLI）
> 结论先行：这个赛道在 2026 年已经**非常拥挤**——Anthropic、OpenAI、Cursor、Kimi、MiniMax、Z.ai 都把「手机/网页遥控本地会话」做成了官方功能，开源侧也有 Happy（23.6k★）、Paseo（15.9k★）、cc-connect（15.3k★）、claudecodeui（13.6k★）这样的大项目。但所有官方方案都是**单厂商锁定 + 必须走厂商官方云 + 使用第三方 API 中转即失效**，而第三方方案要么是「一台机器一个客户端」的手机伴侣，要么是 IM 机器人桥接，**没有一个把「工具无关 + 自建中转 + 多机多会话 fleet 面板 + 真终端 + Windows 被控端服务级保活」放在同一个产品里**。terminalX 的差异化成立，但窗口不大，且必须回答「为什么不用 Paseo / Happier」。

---

## 1. 赛道全景：四种形态

| 形态 | 代表 | 核心逻辑 | 典型短板 |
|---|---|---|---|
| A. 官方「本地会话遥控」 | Claude Code Remote Control、Codex 手机遥控、Cursor Remote Control、Kimi/MiniMax/ZCODE Remote Control | CLI 向厂商云出站轮询，手机/网页通过厂商云回控本地会话 | 只控自家工具；绑定订阅账号；用中转 API 即不可用；一进程一会话 |
| B. 官方「云端沙箱」 | Claude Code on the web、Codex cloud、Cursor Cloud Agents、Devin、Jules、Factory | 任务跑在厂商 VM，与本机无关 | 看不到本地文件/MCP；GitHub 绑定；额度或按量计费 |
| C. 第三方「手机/Web 伴侣客户端」 | Happy、Happier、Paseo、Omnara、CC Pocket、MobileCLI、ServerCC、VibeTunnel、claudecodeui、opencode web、VibeAround | 本机跑守护进程/包装器，经自建或项目方 relay 到 App/浏览器 | 多为单机视角；Windows 支持参差；小团队维护 |
| D. IM 机器人桥接 | Claude Code Channels（官方）、cc-connect、Claude-Code-Remote、claude-client、OpenClaw、OpenACP | 把 CLI stdin/stdout 接到 Telegram/飞书/微信 | 只有聊天，没有终端；消息编辑上限、会话超时；终端必须常驻 |

terminalX 的定位落在 C 与 A 之间：像 A 一样「会话感知」，像 C 一样「自建、工具无关」，再补上 A/C 都没有的「多机 fleet 面板 + Windows 服务级被控端」。

## 2. 官方方案逐项分析

### 2.1 Anthropic：Claude Code Remote Control

- **时间线**：2026-02-25 以 research preview 发布，最初仅 Pro/Max；现文档写明 Pro/Max/Team/Enterprise 均可用，Team/Enterprise 需 Owner 在后台打开开关 [S1][S2]。
- **形态**：三种启动方式——`claude remote-control`（server 模式，可 `--name`、`--spawn worktree`、`--capacity`（默认 32 个并发会话））、`claude --remote-control`（交互会话同时可远程）、会话内 `/remote-control`；VS Code 插件也支持。手机端在 Claude App 的「Code」列表里看到带电脑图标和绿点的会话；会话名默认以主机名做前缀（`myhost-graceful-unicorn`），因此**同一账号下多台机器的会话会混在一个列表里**，但没有「机器」维度的管理 [S1]。
- **网络模型**：本地只发出站 HTTPS，向 Anthropic API 注册并轮询；**会话转录存在 Anthropic 服务器上**；Zero Data Retention 组织不能开启 [S1]。
- **硬性限制**（官方文档原文）[S1]：
  - API key 登录不支持；Bedrock / Vertex（Agent Platform）/ Foundry 不支持；
  - **`ANTHROPIC_BASE_URL` 指向非 `api.anthropic.com` 的主机（LLM gateway / 代理）时不可用，v2.1.196 起强制**——这意味着国内大量使用「中转站」的用户直接被排除；
  - 设置了 `DISABLE_TELEMETRY` / `DO_NOT_TRACK` / `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` 也会关闭该功能；
  - 「One remote session per interactive process」；「Local process must keep running」——关掉终端会话就离线，官方建议远程机器用 tmux/screen 保活（Windows 没有原生 tmux，见 02 报告）；
  - server 模式断网约 10 分钟后进程直接退出；`/plugin`、`/resume` 等命令只能本地执行。
- **它是聊天 UI，不是终端**：手机/网页看到的是对话流、diff、权限审批，不能操作 shell 本身；韩国社区 GeekNews 上 RemoteCode/SSH Term 作者都以此为切入点做产品 [S72]。
- **用户抱怨（GitHub issues，均为 2026 年）**：
  - #34255（03-14，macOS）：长会话 15-60 分钟后静默断连，iOS 端无提示、不自动重连，只能在终端手动断开重连 [S5]；
  - #36401（03-19）：约 5 小时无操作后会话失联且无法恢复，「#1 friction point for mobile-first users」，被标 stale/not planned [S6]；
  - #51267（04-20，**Windows 11**）：会话执行中静默挂起，只有在本地终端按 Esc 才能恢复，「no remote unstick mechanism」，仍 Open；#54076（WSL）被判为其重复 [S7]；
  - #86084（08-12，**Windows 11**）：sessions-bridge 重新初始化时所有已开启 Remote Control 的会话被静默丢弃，「Recovery requires physical access to the desktop machine」[S8]；
  - #70750：从 WSL2 的 `/mnt/c` 路径启动报 Bun ENOENT；#33818：自建 git remote 时报「Failed to convert session context」[S9]。
  - 中文社区评价：「深度绑定 Claude 付费订阅体系，在多会话管理、交互流畅度等方面仍存在不少局限」[S66]；国内用户需要终端能直连 `api.anthropic.com:443`，走中转站的人用不了 [S68][S77]。
- **周边能力**：Cross-session messaging（v2.1.224，2026-08）让不同机器上的会话通过 Remote Control 链路互发消息，但报道称仅 macOS/Linux、不支持 Windows（待核实）[S10]；Dispatch（2026-03-17，Cowork/Desktop 研究预览）用手机给 Mac 桌面派任务，仅 Mac [S11]。

### 2.2 Anthropic：Claude Code on the web 与 Channels

- **Claude Code on the web**：research preview（Pro/Max/Team，Enterprise 需 premium seat）；跑在 Anthropic VM，需要 GitHub（非 GitHub 仓库只能打包上传、不能推回）；与账号其他用量共享速率限制、无单独算力费；`--teleport` 只能云→本地单向；ZDR 组织不可用 [S4]。这是形态 B，和 terminalX 不直接竞争，但它把 claude.ai/code 做成了「云会话 + 本地 Remote Control 会话」的统一列表，是 Anthropic 版的「集中控制台」雏形。
- **Channels**（2026-03-20 research preview）：Telegram / Discord / iMessage 三个官方插件，需要 Bun；配对生成 allowlist；「Events only arrive while the session is open」，常驻要靠 tmux/systemd；仅接受 Anthropic 白名单插件；Team/Enterprise 需管理员开启；Bedrock/Vertex/Foundry 不可用 [S3]。社区实测抱怨：没有主动推送、没有定时、桌面必须开着、每个会话一套配置 [S3]。

### 2.3 OpenAI：Codex cloud / Codex App / ChatGPT 手机遥控 / app-server

- **Codex cloud**（形态 B）：2026-08 时仅 Plus/Pro/Business/Enterprise 可用，Go（$8）不含；2026-04-02 起改为 token 计费；云任务只看到 GitHub/GitLab 仓库，无本地文件/本地 MCP，容器缓存 12 小时后重建（二手来源，待核实）[S19][S20]。
- **手机遥控本地会话**：2026-05-14 ChatGPT iOS/Android 内置 Codex，可遥控 Mac 上的 Codex App；**Windows 主机支持 2026-05-29 才在 Codex App v26.527.1 补上** [S12][S13]。配对需同一 ChatGPT 账号、扫码、电脑保持唤醒，通过 OpenAI relay 中转 [S71]。
- **Windows 仍是二等公民**（openai/codex issues）：#34584（07-21）Windows 桌面端找不到「Set up Remote」，CLI 报 `daemon lifecycle is only supported on Unix platforms` [S14]；#30727 Mac 端新建远程项目时下拉框里看不到已连接的 Windows PC [S15]；#23082（05-16）Windows 上的 SSH 远程项目无法被手机遥控 [S16]；OpenAI 社区有「Windows 已连接但手机端空白无会话」的帖子。
- **需求强度**：Discussion #9200（2026-01-14）190 票、46 人参与，多位用户表示「因为 Claude Code 的 Remote Control 更好而转投 Claude」[S17]。
- **codex CLI 的 remote 能力**：`codex app-server` 是 JSON-RPC 2.0 服务，2026-03 起支持 WebSocket、bearer token、健康检查，可 `codex app-server --listen ws://0.0.0.0:4500`，远端 `codex resume --last --remote ws://…` 保留转录与审批历史；Codex App v26.415（2026-04）内置 SSH 远程项目 [S18]。这是目前**最接近「可自建的 agent 协议端」**的官方能力，terminalX 接 Codex 时应优先走 app-server 而不是刮 TUI。

### 2.4 Cursor / Devin / Factory / Jules

- **Cursor**：Cloud Agents（2026-02-24）+ iOS App（付费计划公测）+ 官方文档里的「Remote Control」——用手机继续驱动本机 agent，「agent loop 上云、工具在本机跑」（二手描述，待核实）；Pro $20 / Pro+ $60 / Ultra $200，云 agent 按模型 API 价扣额度 [S21][S23]。论坛有「让 web/mobile 继续同一个本地 agent 聊天」的长期请求 [S22]。只控 Cursor 自家 agent。
- **Devin**：纯云端（Slack/Linear/Jira 派单，PR 交付），Free / Pro $20 / Max $200，团队版 ACU 计费（多来源数字不一致，待核实）[S24]；不控制用户本机，未见独立手机 App。
- **Factory Droid**：会话在 desktop/web/CLI/IDE 间同步，手机可查看/回复，可分享 live session URL，「Droid Computers」概念（官方页面本次无法直接打开，待核实）[S25]。绑定 Factory 账号。
- **Google Jules**：`jules remote new/list/pull`，任务跑在 Google Cloud VM [S26]；Gemini CLI 的「手机遥控本地会话」请求 #27289（2026-05-19）、#22559 均被 closed as not planned [S27]。

### 2.5 国产/其他模型厂商：Kimi、MiniMax、Z.ai、Grok

- **Kimi Code CLI**：GitHub 上有 #1282、#1964、#2269（2026-05-13）三个 Remote Control 请求，几乎逐条照搬 Claude 文档 [S28][S29]；官方「最新动态」显示已加入实验特性 `KIMI_CODE_EXPERIMENTAL_REMOTE_CONTROL=1` + `kimi rc` / `kimi web --remote-control`（版本与日期待核实）[S30]。
- **MiniMax Code 2.0**：桌面 Agent 基于开源 Pi Agent 重构；官方称手机可连接桌面会话、看终端输出/代码变更、审批权限，2026-07 计划上线（是否已全量待核实）[S31][S32]。
- **ZCODE（Z.ai，2026-06 发布）**：桌面 agent，扫码手机 Remote 视图 + Bot Channel 接微信/飞书/Telegram [S33][S34]。
- **Grok**：社区 `superagent-ai/grok-cli` 提供 `/remote-control → Telegram` 配对、语音转写，CLI 进程必须常驻 [S35]；xAI 官方 Grok Build 的手机遥控有文章报道但本次未能核实 [S70]。

> 小结：**每家厂商都在复制 Claude 的 Remote Control 模式**——出站轮询 + 官方 relay + 自家 App。这验证了需求，也意味着「只控一种工具」的产品没有护城河；同时每家都在自家账号体系里，用户手上有三个 CLI 就要装三个 App。

### 3.2 Web 终端 / Web UI 型

- **VibeTunnel**（4.6k★，MIT）：把 Mac 终端投到浏览器，session recording、活动指示、Git follow；六种穿透方式（Tailscale/ngrok/Cloudflare/Pinggy/Pangolin/局域网）；**「Windows is not yet supported」（issue #252）**，Intel Mac 也不支持原生 App；单机 [S47]。
- **claudecodeui / CloudCLI**（siteboon，13.6k★，**AGPL-3.0**）：Claude Code、Cursor CLI、Codex、OpenCode 的 Web/移动 UI，含聊天、内嵌 shell、文件树、git 面板；自动扫描 `~/.claude` 会话；npm 自托管 / Docker 沙箱 / CloudCLI Cloud（€7/月起）；有 macOS 与 Windows 桌面版；自托管要求机器常开、「Sessions timeout without connection」、工具默认关闭 [S48]。单机实例，没有多机概念；AGPL 对商用二次开发不友好。
- **opencode web / serve**：`opencode web --hostname 0.0.0.0 --port …`，`OPENCODE_SERVER_PASSWORD` 做 HTTP basic auth（不设则裸奔），TUI 只是 server 的客户端，官方建议配合 Tailscale [S49][S50]；只服务 opencode 自身；Windows 官方文档以 WSL 为主（原生支持待核实）。
- **VibeAround**（jazzenchen，525★，MIT）：Tauri 桌面 Hub，一键启动 Claude Code / Codex / Gemini CLI / Pi / OpenCode / Cursor CLI / Kiro / Qwen，多 API profile 并行，PTY+tmux Web 终端，Cloudflare/ngrok/localtunnel/Tailscale Funnel 内置隧道，8 个 IM 渠道 `/pickup` 接管会话；**支持 Windows x64**；单机 Hub、单人维护 [S51]。这是国内最接近 terminalX「被控端」形态的项目，值得借鉴其「API profile + 多 agent 并排」设计。

### 3.3 IM 机器人桥接型

- **cc-connect**（chenhg5，15.3k★，MIT，Go）：10+ agent（Claude Code、Codex、Cursor Agent、Kimi CLI、Qoder、Gemini CLI、OpenCode、iFlow、Pi、Devin、Copilot、ACP）× 13 个 IM（飞书、WPS、钉钉、Slack、Telegram、Discord、企业微信、微博、LINE、QQ、QQ 机器人、Matrix、个人微信）；WebSocket/长轮询「大多数平台不需要公网 IP」；多会话 30 分钟闲置轮换、权限模式、`/dir` 切目录、自然语言定时任务；Windows/macOS/Linux [S55]。国内 IM 桥接的事实标准。
- **Claude-Code-Remote**（JessyTsui，1.3k★，MIT）：hooks 触发邮件/Telegram/LINE 通知，回复邮件注入命令（PTY 或 tmux 注入）；macOS 为主，最后活跃 2025-08 [S54]。
- **claude-client**（Hanson，93★）：飞书 WebSocket 长连接，无需公网 IP；**明确支持 Windows**（用文件轮询绕过 stdout 管道缓冲）；限制：30 分钟会话超时、飞书单条消息约 20 次编辑上限 [S56]。cc-weixin 走微信官方 iLink Bot API [S57]。
- **OpenClaw** 及 openclaw-china 插件（飞书/钉钉/QQ/企微/微信）、飞书官方文章「Lark Coding Agent Bridge」（Claude Code/Codex 接入飞书）、OpenACP（Telegram/Discord/Slack 自托管控制器）[S58][S59][S60]——IM 桥接已经商品化，微信 2026-03 官方接入 OpenClaw「ClawBot」（待核实）。
- 共同短板：只有对话、没有终端；平台消息编辑/频率上限；会话超时轮换；桥接进程和 CLI 都要常驻——**在 Windows 上没有 tmux，这一条就把很多人挡在门外**。

### 3.4 并行编排 / 已退出者

- **Conductor**（YC）：Mac App，git worktree 隔离并行跑 Claude Code / Codex / Cursor agent，免费自带订阅；**Windows 仅 waitlist**；本地桌面工具，不做远程 [S52]。
- **Terragon Labs**：云端后台 agent 编排器（Claude Code、Codex、Amp、Gemini），**2026-01-16 关停**并以 Apache-2.0 开源快照 [S53]。说明「纯云端多 agent 编排」被官方 Claude Code on the web / Codex cloud 挤压。
- **CCSeva**：macOS 菜单栏用量监控，不是远程控制工具，与 terminalX 无直接竞争，但提示「用量/额度可视化」是用户刚需 [S61]。

### 3.5 国内社区自研（V2EX / 掘金 / 腾讯云）

- V2EX 2026-04「如何优雅地用手机远程控制电脑 Claude Code」帖中主流答案是 Happy 与官方 Remote Control [S62]；另有「Roam」（Cloudflare Workers 转发 prompt/输出，手机接续 Claude Code/Codex）[S63]、「可在手机上远程操作 Claude Code/Codex 的终端 App」（5★ 开源）[S64]、腾讯云「手机接管电脑写代码：Claude Code/Codex Remote 平替」（Tailscale + OpenChamber Web UI + opencode）[S65]。共同动机：**官方方案绑订阅/绑网络、Happy 依赖境外 relay、想要自己掌控链路**。（V2EX、知乎、腾讯云页面本次被代理拦截，内容来自搜索摘要，细节待核实。）

## 5. 用户抱怨汇总（按痛点归类）

1. **静默断连 / 挂起，恢复必须回到电脑前**：Claude #34255、#36401、#51267、#86084 全部指向同一件事——远端看不出会话已死，「only local Esc recovers it」「Recovery requires physical access」[S5][S6][S7][S8]。Happy 也有 #982 手机发消息导致会话 SIGTERM [S40]。
2. **Windows 是二等公民**：Codex 手机遥控 Windows 晚 15 天、至今仍有「daemon lifecycle is only supported on Unix」[S14]；Claude 的两起 Windows 11 静默丢会话 issue；跨会话消息不支持 Windows（待核实）[S10]；VibeTunnel、Conductor、Dispatch、Claude-Code-Remote 干脆不支持或 Mac 优先；Happy 的 Windows spawn/PID 复用 bug；IM 桥接要求「终端常驻」而 Windows 没有 tmux。
3. **单厂商锁定**：每个官方遥控只控自家 CLI；Gemini CLI 的遥控请求被 not planned 关闭 [S27]；Codex 用户在 #9200 里说「因为 Claude 有 Remote Control 而换工具」[S17]。用户手上通常同时有 Claude Code + Codex + 一个国产 CLI。
4. **必须走厂商云、账号与网络绑定**：Claude Remote Control 对 API key、Bedrock、`ANTHROPIC_BASE_URL` 中转、ZDR 一律不可用 [S1]；国内用户「终端连不上 api.anthropic.com」是常见帖 [S77]；Codex 遥控要 Plus+ 且同账号；第三方 Happy 默认 relay 在境外且出过 522 全站故障 [S38]。
5. **多机多会话没有「fleet」视角**：官方是「一个进程一个远程会话」，多台机器就是列表里多条同名前缀会话；Codex Mac 端看不到 Windows 主机 [S15]；第三方几乎全是「一 daemon 一 App 页面」。
6. **只有聊天，没有终端**：官方 Remote Control「只能通过聊天界面查看，无法操作终端本身」[S72]，用户为此转向 SSH+tmux 或 ServerCC/VibeTunnel；反过来纯终端方案又没有权限审批/推送。
7. **进程生命周期无人管**：「Local process must keep running」「Sessions timeout without connection」「server 模式断网 10 分钟退出」——没有一个方案把被控端做成系统服务并自动拉起/恢复会话。
8. **安全与许可**：opencode web 不设密码即裸奔；claudecodeui 为安全默认关闭工具且是 AGPL；IM 桥接的 allowlist 若配错等于把 shell 开放给群聊。
9. **IM 桥接体验天花板**：飞书单条消息 ~20 次编辑、30 分钟会话超时 [S56]，Channels 没有主动推送/定时 [S3]。
10. **费用不透明**：Codex cloud 排除 Go 计划、按 token 计费；Cursor 云 agent 按 API 价；Devin ACU；用户于是更愿意「用自己已有订阅在自己机器上跑」，这正是形态 A/C 兴起的原因。

## 6. 空白与差异化判断

### 6.1 已被填满的位置（不要再做）
- 「手机上继续我的 Claude Code 会话」——官方 + Happy + Paseo 已把体验做到不错，且免费。
- 「把 Claude Code 接进飞书/微信」——cc-connect、OpenClaw、飞书官方 bridge 已经商品化。
- 「云端并行跑很多 agent 出 PR」——Claude Code on the web / Codex cloud / Cursor Cloud 直接内置，Terragon 已倒。

### 6.2 仍然空着的位置
1. **多机 fleet 控制台**：没有任何方案回答「我有 3 台 Windows 工作站 + 2 台 Linux 盒子，每台跑着 2-4 个不同厂商的 agent，我要在一个页面看谁在等审批、谁挂了、谁用量快满了」。官方是会话列表不是机器列表；第三方是单 daemon。
2. **Windows 被控端「服务级」保活与恢复**：所有方案都假设有 tmux/常驻终端；在 Windows 上把被控端做成服务、崩溃自动重启、会话断点恢复、远端可「unstick」（发送 Esc/Ctrl-C/重启会话），是一个明确的、issue 里反复被点名的空白。
3. **工具无关 + 自建中转 + 中转 API 友好**：官方遥控在 `ANTHROPIC_BASE_URL` 非官方时直接禁用，而国内相当比例的 Claude Code 用户正是走中转的；terminalX 自建 relay 天然绕开这一限制，并且同一被控端可以同时托管 Claude Code、Codex（走 app-server）、Kimi、MiniMax、Grok、opencode。
4. **「真终端 + agent 感知」双视图**：官方只有聊天，VibeTunnel 只有终端。两者并存（终端 pane + 从输出/hook/协议解析出的「等待审批/已完成/出错」状态 + 推送）目前只有 VibeAround 单机做了雏形。
5. **团队/远程办公语境**：审计日志、谁能控哪台机、审批权限分级、会话共享——只有 Factory/Happier 提了企业认证，其余全是个人玩具。

### 6.3 terminalX 的差异化是否成立
- **成立，但必须以「多机 + Windows + 工具无关 + 自建」四项同时兑现为前提**。只做其中一两项，就会被 Paseo（工具无关、可自建、Windows 桌面）或 Happier（多工具、自建 relay、跨机 handoff）覆盖。
- **最大的威胁是 Paseo**：15.9k★、Apache-2.0、daemon 架构与 terminalX 的「被控端 + relay + 多端」几乎同构。terminalX 需要明确回答：(a) fleet 视角（机器/会话/用量/告警一屏）；(b) Windows 服务化与远程解卡；(c) 真终端；(d) 中文 IM 与国内网络友好。
- **官方的追赶方向**：Claude server 模式已支持单机 32 并发 + 跨机消息；Codex app-server 已是可远程的 WebSocket 服务。厂商会把「单厂商多会话」做得越来越好，但不会做「跨厂商」和「走第三方中转」——这是 terminalX 相对官方的结构性护城河。

## 7. 对 terminalX 的启示（可直接进设计阶段）

1. **被控端 = Windows 服务 + 会话管理器**：以 ConPTY 托管每个 agent 会话，进程树纳入 job object，崩溃自动重启；提供远程「Esc / Ctrl-C / kill & resume」按钮，正面回应 #51267/#86084 类问题。
2. **接入层按协议分级**：Codex 走 `codex app-server`（JSON-RPC/WS）；opencode 走 `opencode serve` HTTP API；Claude Code/Kimi/MiniMax/Grok 先走 PTY + hooks/输出解析，后续接 ACP。Happier 和 cc-connect 都把 ACP 当作「任意 agent」的兜底，值得跟进。
3. **控制台以「机器」为一级实体，会话为二级**：状态（在线/离线/等待审批/出错）、用量（借鉴 CCSeva/Usagebar）、最近活动、一键接管；这是所有竞品缺失的视图。
4. **中转必须可自建且默认就是自建**：官方 relay 的所有限制（订阅、API key、中转 URL、ZDR）都变成 terminalX 的卖点；同时给出「一键部署 relay（Docker / 单二进制）」，参考 happy-on-aws 的一键部署与 Paseo 的 E2E relay。
5. **双视图 UI**：左侧真终端（xterm.js），右侧 agent 事件流（审批卡片、diff、通知），手机上折叠为卡片优先。
6. **通知与 IM 作为通道而非产品**：推送 / Telegram / 飞书 / 企微 只做「告警 + 一键回到 Web 控制台」，不重复 cc-connect 的完整聊天桥接。
7. **安全默认值**：出站连接、E2E 或至少 relay 端零明文、设备配对 + allowlist、审批权限分级、审计日志——这些是从 opencode 裸奔、Channels allowlist 教训中总结的最低要求。
8. **许可与商业化**：避开 AGPL 依赖（claudecodeui）；核心开源 + 托管 relay/团队功能收费是 Happy/Omnara/CloudCLI 走过的路，CloudCLI €7/月、Omnara $9/月、MobileCLI $20/年可作定价锚点。
