# 05 · 技术可行性与安全架构：Web 控制 Windows 终端的选型、风险与 MVP 范围

> 调研日期：2026-09-03 ｜ 面向：terminalX 第一阶段（一个 Web 页面控制 Windows 电脑上的终端 + AI CLI），并为后续「自建中转 + 多端」预留架构。
> 说明：本环境的 WebSearch 配额已耗尽，本文全部以 **直接打开一手来源**（GitHub 仓库/源码/Issue、npm / crates.io 注册表 API、官方文档站）核实；learn.microsoft.com、devblogs、rustdesk.com、tailscale.com、docs.rs、bun.sh 等域名被代理拦截，改用其 GitHub 镜像或注册表 API。所有版本号与日期均来自注册表/发布页（2026-09-03 查询）；无法核实的数字标「待核实」。
> 结论先行：**Windows 侧底层已经成熟（ConPTY 自 Win10 1809 起内置，node-pty / portable-pty 都能开箱用），前端 xterm.js 6.x 是唯一合理选择，传输层第一阶段用「被控端出站 WSS → 自建中转 → 浏览器」即可；真正的难点在三处：ConPTY 的行为怪癖、xterm.js 移动端输入、以及「中转不可窥探」的端到端加密设计。**

## 0. 一页结论

1. **Windows 终端底层不是风险。** ConPTY 自 Windows 10 1809 起内置；node-pty 1.1.0（2025-12-22）已彻底移除 winpty，仅支持 ConPTY，并可选装载自带的 `conpty.dll`（`useConptyDll`）[S3][S4][S5]；Rust 的 `portable-pty` 0.9.0（wezterm 出品，1370 万下载）在 Windows 上同样走 ConPTY [S8]；Go 只有薄封装（`UserExistsError/conpty`、`charmbracelet/x/xpty`）[S10][S11]。Win32-OpenSSH 的 sshd 以 Windows 服务身份跑 ConPTY 已多年，证明「服务 + ConPTY」可行 [S14]。
2. **前端只有 xterm.js（或其 API 兼容替身 ghostty-web）。** `@xterm/xterm` 6.0.0（2025-12-22）移除 canvas 渲染器、加入 DEC 2026 同步输出、ESM；fit 0.11 / webgl 0.19 / search 0.16 / serialize 0.14 全部同日发布 [S1][S2]。移动端软键盘是 xterm.js 自 2022 年起的「help wanted」级别的老大难（Android Chrome 组合事件 #3600、触屏复制 #3727、Android 外接键盘重复 #5438 排到 7.0.0）[S27][S28][S29]——**terminalX 必须自建输入层（隐藏 input + 虚拟键条），不能指望上游修好。**
3. **传输层第一阶段用 WebSocket 经中转，不做 P2P。** Claude Code Remote Control 的做法就是「本地进程只发出站 HTTPS，不开任何入站端口，服务器在两端之间路由消息」[S22]；RustDesk / Tailscale 也都把中继当作保底并花大量精力做打洞 [S43][S48]。WebRTC DataChannel（pion v4 / Rust `webrtc` 0.21）留到第二阶段做「可选直连加速」，浏览器端天然具备，被控端 Go/Rust 都有纯实现 [S50][S51]。
4. **安全设计的两条硬线：中转不能看内容、被控端只出站。** sshx（Argon2id + AES-CTR，密钥放在 URL `#` 片段）、Happy（tweetnacl + @noble/ed25519，服务器只存密文 blob）、RustDesk（sodiumoxide/NaCl，服务器 Ed25519 密钥签发对端公钥）三种做法都已被开源验证 [S37][S42][S45][S46]。RustDesk 客户端在验签失败时会「记录错误并继续以未加密方式握手」——terminalX 要吸取教训做 **fail-closed**。
5. **被控端语言推荐 Rust（备选 Go），服务端 Rust/Go 皆可，前端 React + xterm.js。** Node 方案（node-pty 最成熟）输在分发：Node SEA 仍是「Active Development（Stability 1.1）」且原生插件要落盘 dlopen [S53]；Bun `--compile` 能嵌 `.node` 但官方自认「二进制还是太大」[S54]。Rust 有 sshx / RustDesk / Zellij / wezterm 四个同类先例，`portable-pty` + `tokio-tungstenite` 0.30 + `windows-service` 0.8.1 + `snow`（Noise）0.10 全部现成 [S8][S17][S52][S55]。
6. **4–6 周 MVP 可交付范围**：单机 Windows Agent（用户态自启，非服务）+ 单节点中转 + Web 页面（多标签、断线重连、回滚缓冲、移动端键条）+ 设备一次性配对码 + TLS + 会话级对称加密（sshx 式）。服务化、P2P、Passkey、审计回放放二期。

## 1. Windows 终端底层

### 1.1 ConPTY 现状与要点

- **版本门槛**：ConPTY（`CreatePseudoConsole` / `ResizePseudoConsole` / `ClosePseudoConsole`）随 Windows 10 1809 内置。node-pty 类型注释写明「ConPTY 从 build 17134 就有但太不稳定，默认在 build ≥ 18309 才启用」，README 要求「Windows 10 1809 (build 18309) 或更新」[S3][S4]。Claude Code 原生 Windows 版本的系统要求也恰好是 Windows 10 1809+ / Server 2019+ [S21]——两者门槛一致，terminalX 直接把 **Win10 1809+** 作为最低支持版本即可。
- **自带 conpty.dll vs 系统内置**：node-pty 自 PR #694（2024）起随包分发 `conpty.dll` + `OpenConsole.exe`，opt-in 选项 `useConptyDll`（1.2.0-beta.12 更新到 conpty 1.25.260303002）[S5][S6]。好处是新修复不依赖用户 Windows 版本；坏处已有实证：Issue #894（2026）报告 PowerShell 7 下自带 DLL 首屏延迟约 3.5 s，而系统 ConPTY 仅 340 ms，但系统 ConPTY 又有 IME 候选框闪烁 [S7]。**结论：Agent 启动时做可配置的双路径（系统 ConPTY 默认，异常时切自带 DLL），并把「首屏时间」纳入 MVP 验收指标。**
- **已知怪癖**（会影响 Web 终端体验）：
  - Resize 时 ConPTY 会重绘整个屏幕缓冲区，Win32-OpenSSH 文档直言「Windows 10 conhost.exe 有 bug 导致窗口缩放有问题」[S14]；xterm.js 为此提供 `windowsPty: { backend: 'conpty', buildNumber }` 选项来开启针对 Windows 的启发式修正 [S30]。
  - 在 WSL 里通过 ConPTY 运行 Win32 程序（如 `cmd.exe`）会残留 Win32 输入模式并卡 3 秒等待 DA1 应答（microsoft/terminal #17822，2024-08 至今 open）[S12]——**不要用「先起 WSL 再在里面调 Windows 程序」的混合方案。**
  - ConPTY 与 `CreateProcessWithLogon` / `CreateProcessWithToken` 搭配存在问题（#11865，2021 至今 open）[S13]——这直接影响「服务进程替登录用户起 shell」的实现（见 1.3）。
  - ttyd 在 Windows 11 上有未解决的连接失败报告（#1207，ttyd 自 1.7.0 起原生支持 Windows 但要求 ConPTY）[S34]。
- **流控**：node-pty 提供 `handleFlowControl` + XON/XOFF（`\x13`/`\x11`）[S3][S4]。AI CLI（Ink 全量重绘，见 04 号调研）输出量大，Agent → 浏览器方向必须有背压，否则弱网手机端会被淹没。

### 1.2 PTY 库对比

| Rust | `portable-pty` | 0.9.0（2025-02-11），1374 万下载 [S8] | 高（wezterm 每日在 Windows 上使用） | 统一 `native_pty_system()` API，Windows 走 ConPTY |

### 1.3 默认 Shell 取舍（PowerShell 7 / cmd / WSL / Git Bash）

| 选项 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| **PowerShell 7 (pwsh)** | 现代、跨平台、ANSI/VT 支持好；最新稳定版 7.6.5（2026-08-14）[S26]；Claude Code / Codex 官方 Windows 安装器都是 PowerShell 一行命令 [S21][S23] | 需额外安装（Win 内置的是 5.1） | **默认 shell 首选，检测不到则回退 Windows PowerShell 5.1** |
| cmd.exe | 零依赖 | 无现代补全、脚本能力弱 | 仅作保底 |
| Git Bash | Claude Code 的 Bash 工具依赖它，「装了 Git for Windows 就用 Git Bash，否则用 PowerShell 工具」[S21] | 非系统组件，路径需探测（`CLAUDE_CODE_GIT_BASH_PATH`） | 作为可选 shell 列出，自动探测 `C:\Program Files\Git\bin\bash.exe` |
| WSL 2 | Linux 工具链；Claude Code 的 sandboxing 只在 WSL2 下支持 [S21] | 是另一台「虚拟机」，与 Windows 文件系统/凭据割裂；混合调用有 #17822 坑 [S12] | 作为独立 shell 类型（`wsl.exe -d <distro>`）提供，不做混合 |

实现上可仿照 Win32-OpenSSH 的 `DefaultShell` / `DefaultShellCommandOption` 注册表约定（`HKLM\SOFTWARE\OpenSSH`）[S15]：terminalX 在 Agent 配置里保存「shell 路径 + 参数模板」，前端新建标签时可选。

AI CLI 在 Windows 的落地情况（决定 shell 默认值）：Claude Code 原生 Windows，支持 Bash/Zsh/PowerShell/CMD [S21]；Codex CLI 官方支持 Mac/Linux/Windows，提供 `install.ps1` [S23]；社区 grok-cli 基于 TypeScript + Bun，文档未提 Windows [S24]；MiniMax Code 是 macOS/Windows 桌面 App，不是 CLI [S25]。

### 1.4 Windows 服务、锁屏、UAC、Defender

- **服务 vs 用户态自启**：Windows 服务运行在 Session 0，与用户桌面隔离（Vista 起）。ConPTY 本身不需要可见窗口，所以「服务托管 ConPTY」可行——Win32-OpenSSH 的 sshd 正是以服务身份在 1809+ 上用 ConPTY 起用户 shell [S14]。但 AI CLI 需要读用户目录下的配置与凭据（`~/.claude`、npm 全局目录等），shell 必须以 **登录用户的 token** 运行，这就要 `WTSQueryUserToken` + `CreateProcessAsUser`，而 ConPTY 与 token 类 API 组合的 issue #11865 仍 open [S13]。**建议：MVP 用「用户态自启（任务计划程序 / 启动项，登录即起）」，二期再做「服务作为看门狗 + 用户会话内的 PTY host 进程」的双进程结构。** Go 的 `kardianos/service`（4.8k star，含「是否交互式运行」检测）[S16] 与 Rust 的 `windows-service` 0.8.1（Mullvad 维护）[S17] 都能覆盖服务安装/启停。
- **锁屏后可用**：ConPTY 进程不依赖交互桌面，锁屏不影响；真正的杀手是 **睡眠/休眠**——Agent 安装向导应提示关闭睡眠或提供「保持唤醒」开关（`SetThreadExecutionState`，待在 MVP 中实测）。
- **UAC**：Agent 不以管理员运行；远程无法看到安全桌面上的 UAC 弹窗，需在 UI 明示「需要提权的命令请在本机操作」。Windows 11 24H2 起自带 `sudo`（microsoft/terminal #146 已关闭并标记 fix available）[S13-b]，可作为「内联提权」的可选路径（具体行为待核实）。
- **Defender / SmartScreen 误报**：Go 官方 FAQ 承认「商业杀软常被 Go 二进制的结构搞糊涂」[S18]，golang/go 有多起 Defender 误报 issue（#51514 2022、#48224 2021、#45415 2021）[S19]；Rust 侧 2025 年 #147547（Wacatac 误报，疑与 PE 证书偏移有关）[S20]。**规避：Authenticode 代码签名（Claude Code 的 Windows 二进制就签为 "Anthropic, PBC"[S21]）、不使用 UPX、向 Microsoft 提交误报样本、首发通过 winget 分发。** 证书费用与 EV/Azure Trusted Signing 的价格待核实。

关键 API：`attachCustomKeyEventHandler`（在 xterm 处理前拦截按键，实现 Ctrl/方向键条）、`input(data)`（以「用户输入」语义注入数据，触发 `onData`）、`textarea`（承接输入的隐藏 textarea）、`scrollback`（默认 1000 行）[S30]。

替代方案：**ghostty-web**（Coder 出品，Ghostty 终端核心编译为 WASM，~400 KB，「把 import 从 `@xterm/xterm` 改为 `ghostty-web` 即可迁移」，MIT，2.8k star）[S31]，VibeTunnel 已采用 [S41]。建议 MVP 用 xterm.js（生态/插件齐），保留接口以便 A/B。

### 2.2 移动端软键盘、方向键、Ctrl 键

上游现状（全部为 area/mobile 标签）：
- #3600（2022-01 至今 open，help wanted）：Android Chrome + GBoard「不可靠地触发 key 事件，还会在 Enter/Backspace 周围包一堆 composition 事件」，导致重复/乱序字符；建议参考 CodeMirror 的 DOM observer 方案 [S27]。
- #3727（2022-04 至今 open）：iPad/iPhone 触屏无法选择/复制 [S28]。
- #5438（2025-11，排到 7.0.0 里程碑）：Android 外接键盘同时按两键出现重复 [S29]。
- #5721（2026-02 已关闭）：iPad Safari 硬件键盘 Ctrl-C 被送成 keyCode 13 [S29-b]。

**terminalX 的方案（参考 Zellij web client 与 RustDesk 终端模式）**：
1. 手机端不让 xterm 的 textarea 直接接软键盘，改用自管的隐藏 `<input>`：监听 `beforeinput`/`compositionend`，把最终文本通过 `term.input()` 送出，绕开组合事件乱序。
2. 屏幕底部固定「虚拟键条」：Esc、Tab、Ctrl（粘滞）、Alt、↑↓←→、PgUp/PgDn、`|` `~` `/`、Ctrl-C、Ctrl-D、Ctrl-Z、粘贴；Ctrl 粘滞时通过 `attachCustomKeyEventHandler` 把下一个字母转成控制字符。Zellij 0.43 的 web client 就「自动检测移动端浏览器并提供触屏 UI：视口缩放、屏幕键盘、窗格/标签选择器」[S32]。
3. 触屏选择/复制：提供「选择模式」按钮，用 `addon-serialize` 或自绘选区导出文本，不依赖原生选区。
4. 视口：`visualViewport` resize 时调用 fit，避免键盘弹出后终端被顶出屏幕。

### 2.3 回放 / 滚动缓冲 / 多标签

- **服务端权威缓冲**：Agent 为每个会话维护环形缓冲（建议 2–8 MB 或 N 万行，可配）+ 单调序号；浏览器重连时带上「已收到的最后序号」，Agent 只补差（Eternal Terminal 的序号语义 [S39]）。首次打开时 Agent 发送「快照」（用 xterm.js 无头实例 + `addon-serialize` 生成，或直接回放尾部缓冲）。
- **录制**：二期用 asciinema v2 格式（VibeTunnel 现成做法）[S41]，既是审计也是回放。
- **多标签/多机**：一个 WebSocket 复用多个会话（帧头带 sessionId），前端每个标签一个 xterm 实例；后台标签停止渲染但继续接收（或让 Agent 只发摘要）。Zellij 的「URL 即会话：访问 `/session-name` 自动创建/附加/复活」值得借鉴 [S32]。

## 3. 传输层：中转 WebSocket vs WebRTC vs 自研 P2P

### 3.1 方案对比

| 维度 | WSS 经自建中转 | WebRTC DataChannel P2P | RustDesk 式自研（TCP 打洞 + 中继） | Tailscale/DERP 式 |
|---|---|---|---|---|
| 浏览器可用 | 原生 | 原生 | 需 WS 网关（RustDesk web 端走 21118/21119 WS 端口）[S44] | 不适用于纯浏览器 |
| 被控端实现 | 任何语言几行 | Go: pion v4（纯 Go、无 cgo，16.8k star）[S50]；Rust: `webrtc` 0.21.0-rc.1（2026-08-31）[S51] | 自己写 rendezvous + 打洞 + 中继（RustDesk hbbs/hbbr）[S43] | 需 WireGuard 栈 |
| NAT 穿透 | 不需要（两端都出站） | ICE + STUN；对称 NAT 需 TURN（= 中继） | UDP/TCP 打洞，失败走 hbbr；`ALWAYS_USE_RELAY=Y` 可强制中继 [S43] | 打洞失败走 DERP，「DERP 是最后手段」[S48] |
| 延迟 | 多一跳（国内自建节点通常 20–60 ms，待实测） | 直连最低 | 直连最低 | 直连最低 |
| 企业网络友好 | 最好（443 出站） | 常被禁 UDP；TURN over TCP/TLS 可救 | UDP 常被禁 | 同左 |
| 中转成本 | 全量流量过中转（终端流量极小，KB/s 级） | 只有信令过服务器 | 中继流量取决于打洞成功率 | 同左 |
| 复杂度 | 最低 | 中（信令、ICE 重启、断线检测） | 高 | 高 |

libp2p 的经验值得记住：打洞需要 AutoNAT（探测可达性）+ Circuit Relay v2（先经中继建连）+ DCUtR（CONNECT/SYNC，按 RTT/2 同步对拨），规范自述「UDP 效果好，TCP 尚可」[S49]；punchr 测量项目未在 README 给出成功率数字（待核实）。**结论：终端流量小、对延迟不极端敏感、企业网络要求高——第一阶段 100% 走中转，二期把 WebRTC DataChannel 作为「可选直连」叠加（信令复用现有 WS）。**

### 3.2 断线重连与会话保持（tmux 的 detach/attach 语义）

- **PTY 生命周期与连接解耦**：会话由 Agent 持有，浏览器断开只是「detach」；显式「关闭标签」才 kill 进程。参考 sshx：断线后指数退避 2 s→16 s，连上 10 s 后计数归零，且每 60 s 主动重连以配合服务端滚动发布 [S37]。
- **心跳与状态**：Claude Code Remote Control 的经验——「presence 心跳失败约 30 分钟后才断开、期间持续重注册」「服务器 403 时重试最多 3 分钟」「服务停止后 4 小时内可恢复会话」[S22]。terminalX 可取：Agent 侧 WS 心跳 15–30 s，中转对 Agent 离线保留元数据 ≥ 4 小时，浏览器侧显示「Agent 离线，缓冲已保留」。
- **多端同时附着**：同一会话允许多个浏览器同时 attach（Web + 手机），输入合并、输出广播；尺寸取「最小公共尺寸」或以最后输入者为准（tmux 的 `aggressive-resize` 思路）。
- **Windows 特有**：Eternal Terminal 与 mosh 都只支持 WSL，不支持原生 Windows [S39][S40]，因此 terminalX 的「保活」必须自己在 Agent 里做，不能借用它们。

## 4. 安全架构

### 4.1 开源先例怎么做端到端加密

| 项目 | 密钥来源 | 算法 | 服务器能看到什么 | 备注 |
|---|---|---|---|---|
| sshx | 随机密钥放在 URL `#` 片段（`resp.url + "#" + encryption_key`），浏览器不会把片段发给服务器 | Argon2id（19456 KiB, t=2, p=1，固定盐）→ 16 字节 → AES-128-CTR，流号做 IV [S37] | 只见密文与会话元数据；官方「不支持自托管」 | 只读/可写用逗号追加 write_password |
| Happy | 客户端生成密钥，手机扫 QR 配对 | `tweetnacl` + `@noble/ed25519` + `@noble/hashes` [S42] | 「会话元数据、agent 状态、消息内容均为不透明加密 blob」，服务器只存公钥与账户元数据 [S42] | 传输 Socket.IO；自托管版 `happy server` 用嵌入式 PGlite，无需 Postgres/Redis/S3 [S42] |
| RustDesk | 服务器 Ed25519 密钥（`id_ed25519`）签发对端 ID+公钥；客户端用服务器公钥 `rs_pk` 验签后，用 sealed box 封装对称密钥 | sodiumoxide 0.2（NaCl） [S45][S46] | 中继 hbbr 只转发密文；但客户端验签失败时「记录错误、发送空消息并继续」而非终止 [S45] | 服务器公钥需手工配置到客户端（`Key` 字段）[S44] |
| Tailscale DERP | WireGuard 节点密钥（curve25519） | WireGuard | 「只看到加密的 WireGuard 包，因此对网络级调试没用」[S48] | derper 自托管需 80/443 TCP + 3478 UDP |

### 4.2 terminalX 的安全分层（建议）

| 层 | 措施 | 阶段 |
|---|---|---|
| 传输 | 全部 TLS 1.3（浏览器 WSS、Agent WSS）；Agent **只出站**，不开入站端口（与 Claude Code RC 一致 [S22]） | MVP |
| 设备配对 | 首次配对：Web 端生成 8–10 位一次性码 / 二维码（含中转地址 + 配对密钥），Agent 输入后换取长期设备证书；配对码 5 分钟过期、一次有效（Happy/Claude RC 均用二维码 [S22][S42]） | MVP |
| 端到端加密 | v1：配对时协商的会话根密钥 → HKDF 派生方向密钥 → AES-256-GCM 逐帧加密（浏览器用 WebCrypto 原生，Agent 用 ring/aes-gcm），中转只见帧头（sessionId、序号、长度）；v2：Noise XX（`Noise_XX_25519_ChaChaPoly_SHA256`）做双向静态密钥认证 + 前向保密，Rust `snow` 0.10 现成 [S52] | MVP(v1) / 二期(v2) |
| 中转 ↔ Agent 身份 | mTLS：配对成功后签发设备证书（内部 CA），中转按证书指纹路由，被吊销即断 | MVP（简化版 token）/ 二期（mTLS） |
| 用户认证 | 账号 + TOTP；Passkey/WebAuthn（W3C 规范 [S56]）作为二期；参考 Claude RC 的「登录 18 小时后需 Face ID/Touch ID/Windows Hello/Passkey 步进」[S22] | 二期 |
| 授权粒度 | 每台机器/每个会话可标只读（ttyd 1.7.4 起默认只读需 `-W`；gotty `--permit-write`；tmate 只读链接 [S34][S35][S38]） | MVP（只读开关） |
| 审计 | 中转记录：谁、何时、连了哪台机、哪个会话、字节数（不记内容）；Agent 本地可选录制 asciinema，密钥归用户 | MVP（元数据）/ 二期（录制） |
| Fail-closed | 密钥/证书校验失败一律断开，不降级明文（吸取 RustDesk 教训 [S45]） | MVP |
| 企业合规 | 提供「自托管中转」+「禁用远程」开关（Claude RC 有 `disableRemoteControl`，且 Zero Data Retention 组织无法启用 RC [S22]）；文档写明数据流向 | MVP 文档 / 二期功能 |

### 4.3 中转节点的边界

- 中转只做三件事：认证与路由、离线元数据保留、指标；**不解密业务帧**。RustDesk 文档特别提醒：开放 WS 端口时 hbbs/hbbr 会信任 `X-Real-IP`/`X-Forwarded-For`，必须只通过反向代理暴露 [S44]——terminalX 的中转同样要把「真实 IP 判定」和「反代信任列表」写死。
- 单节点即可起步（RustDesk 自述「最低配云主机足够」[S44]）；多节点时让 Agent 与浏览器各选就近节点、节点间 mesh 转发（DERP 的 home region 思路 [S48]）。

## 5. 技术选型

### 5.1 被控端 Agent：Go / Rust / Node

| 维度 | Rust | Go | Node（Bun/SEA 打包） |
|---|---|---|---|
| ConPTY 库 | `portable-pty` 0.9.0（wezterm）[S8] | 薄封装，需自补 [S10][S11] | `node-pty` 最成熟 [S3] |
| 单文件分发 | 原生；体积小（数 MB） | 原生；无 cgo（pion 亦无 cgo）[S50] | Node SEA「Active Development」，原生插件需当作 asset 落盘再 `dlopen` [S53]；Bun `--compile` 支持嵌入 `.node`、`--windows-hide-console`、`--windows-icon`，但官方称「二进制还是太大」[S54] |
| Windows 服务 | `windows-service` 0.8.1 [S17] | `kardianos/service` [S16] | 需借助 nssm/WinSW 或自写 |
| 端到端加密 | `snow`、`ring`、`x25519-dalek` 齐全 [S52] | `golang.org/x/crypto` 齐全 | `tweetnacl`/`@noble/*`（Happy 用法）[S42] |
| WebRTC（二期） | `webrtc` 0.21（RustDesk 也依赖其 0.14 版本 [S46]） | pion v4 [S50] | node-datachannel（待核实） |
| 同类先例 | sshx、RustDesk、Zellij、wezterm | ttyd(C)/gotty、Tailscale | VibeTunnel（Windows 尚未支持 [S41]）、Happy、wetty |
| 内存安全 / 长期常驻 | 最好 | 好 | 一般（GC 停顿可接受，但 node-pty 仍有 teardown 泄漏 issue [S6]） |
| 开发速度 | 慢（编译、借用检查） | 快 | 快 |
| Defender 误报 | 有案例 [S20] | 有案例 [S18][S19] | 打包器产物更易被误报（待核实） |

**推荐：Rust。** 理由：① `portable-pty` 是四个候选里「被大规模 Windows 用户日常使用」且非 Node 的唯一成熟 PTY 库；② sshx 已证明「Rust CLI + Rust 中转 + 浏览器」的整套架构可行；③ Agent 是长期常驻、持有用户凭据的进程，内存安全价值高；④ 密码学与 Noise 生态现成。**备选 Go**：若团队更熟 Go，用 `charmbracelet/x/xpty` + pion，开发速度更快，代价是自己补 ConPTY 细节。**不推荐 Node 做 Agent**（分发与服务化是硬伤），但 node-pty 的 ConPTY 处理代码值得作为实现参考。

### 5.2 服务端（中转）

- Rust（axum + tokio-tungstenite 0.30）或 Go（net/http + WebSocket）皆可；中转逻辑本身很薄。建议与 Agent 同语言（Rust）以共享协议定义（protobuf/serde 类型），避免双份帧格式实现漂移。
- 存储：MVP 用 SQLite（设备、配对、会话元数据、审计）；Happy 自托管版用嵌入式 PGlite 的思路说明「单机零依赖」是被验证的路线 [S42]。
- 部署：单二进制 + systemd/docker；域名 + 自动证书（Caddy/acme）。

### 5.3 前端

- React 18 + TypeScript + Vite；`@xterm/xterm` 6.0 + fit/webgl/search/serialize/web-links/clipboard/unicode11；状态管理轻量（zustand）；PWA 以便手机「添加到主屏」。
- 协议：单条 WSS 上的二进制帧（1 字节类型 + sessionId + 序号 + 密文），不用 JSON 传终端字节。

### 5.4 协议草案（供架构文档细化）

```
帧头（明文）: ver u8 | type u8 | session u32 | seq u64 | len u32
帧体（密文）: AES-256-GCM(nonce = dir||seq, key = HKDF(root, dir))
type: 0x01 Data(Agent→Web) 0x02 Input(Web→Agent) 0x03 Resize 0x04 Open 0x05 Close
      0x06 Ack(seq) 0x07 Snapshot 0x08 Ping/Pong 0x09 Meta(JSON, 明文允许: 机器名/shell 列表)
```

## 7. 第一阶段 MVP（4–6 周）技术范围

**目标**：一个 Web 页面控制一台 Windows 电脑上的多个终端/AI CLI 会话，断线不丢会话，手机可用。

| 周 | 交付 | 验收 |
|---|---|---|
| 1 | Agent 骨架：Rust + `portable-pty` 起 pwsh/cmd/Git Bash/WSL；本地 WS 直连调试页；环形缓冲 + 序号 | 四种 shell 可交互；`claude`、`codex` 在 pwsh 下可正常运行并显示 TUI |
| 2 | 中转：设备注册、配对码、路由、心跳、离线元数据；TLS；SQLite | 两端都在 NAT 后可连；Agent 重启后自动重连 |
| 3 | Web：React + xterm.js 6 + fit/webgl/search/serialize；多标签；重连补差；快照 | 断网 30 s 恢复后无丢字；1 万行输出不卡 |
| 4 | 端到端加密 v1（配对根密钥 → HKDF → AES-GCM）；只读附着；审计元数据 | 中转抓包只见帧头；错误密钥 fail-closed |
| 5 | 移动端：隐藏 input + 虚拟键条 + 视口处理；PWA | iOS Safari / Android Chrome 真机可输入 Ctrl-C、方向键、中文 |
| 6（缓冲） | 安装器（winget/MSI 或单 exe + 任务计划自启）、代码签名、文档；性能与首屏指标 | 首屏 < 1 s（系统 ConPTY 路径）；Defender 无拦截 |

**明确不做（放二期）**：Windows 服务化与用户会话切换、WebRTC 直连、Passkey、录制回放、多中转节点、多机 fleet 面板的复杂功能（MVP 只做列表与切换）、文件传输（可借鉴 ttyd 的 trzsz [S34]）。

## 8. 对 terminalX 的机会点（可借鉴设计）

1. **「URL 即会话」**（Zellij web client）：`/m/<machine>/<session>` 直接创建/附加/复活，天然可收藏、可分享只读链接 [S32]。
2. **「密钥在片段、服务器零知识」**（sshx）：分享链接时把会话密钥放在 `#` 后，中转永远拿不到 [S37]。
3. **「出站轮询 + 短期凭据 + 设备信任步进」**（Claude Code Remote Control）：安全模型可直接对标，且 RC 不支持 API Key/网关/ZDR 组织的空白正是自建中转的卖点 [S22]。
4. **「自托管一条命令」**（Happy `happy server`，嵌入式数据库）[S42]：降低企业/个人自建门槛。
5. **「自带 conpty.dll 的可切换路径」**（node-pty `useConptyDll`）：把 Windows 版本差异从用户侧挪到产品侧 [S4]。
6. **「只读默认、显式开写」**（ttyd 1.7.4 起）[S34]：分享给同事看 AI 干活时零风险。
7. **「移动端触屏 UI 自动切换」**（Zellij）+「浮动快捷键」（RustDesk 1.4.1 终端模式，见 01 号调研）。
