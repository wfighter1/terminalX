# 01 · 市场调研总览与痛点分析

> 日期：2026-09-03 ｜ 产品：terminalX（多端远程操作 PC 上的 AI CLI：Claude Code / Codex CLI / Grok Build / MiniMax 等；服务端自建中转 + 控制端/被控端；第一阶段 = 一个 Web 页面控制 Windows 电脑上的终端）
> 依据：`docs/research/01–06` 六份分项调研。本文写作时 WebSearch 配额已耗尽，改以 WebFetch 直接打开一手来源复核了 16 处关键论断（Claude Code Remote Control 与 Agent View 官方文档、Win32-OpenSSH #2291、claude-code #34255/#29214/#30154/#77252、codex #22757 与 Discussion #9200、Happy/Paseo/cc-connect 仓库、Zellij releases 等）。国内媒体（新浪/知乎/V2EX）域名被代理拦截，价格与免费额度类数字沿用分项报告并标「待核实」。

## 0. 一页结论

1. **三类方案传输的东西不同：GUI 远程传像素，终端远程传字节，AI 代理遥控传事件。** AI CLI 远程办公真正需要的是「事件 + 字节」两层：知道 agent 何时在等我（事件），必要时能进终端敲键（字节）。像素方案在这两层都是绕路。
2. **赛道已拥挤但结构性空位仍在。** 官方遥控（Anthropic 2026-02、OpenAI 2026-05、Cursor/Kimi/MiniMax/Z.ai 跟进）全部「单厂商 + 官方云 + 订阅账号」；开源侧 Happy 23.6k★、Paseo 15.9k★、cc-connect 15.3k★ 各解决一部分。**没有一个产品同时具备：多机 fleet 视图 + Windows 原生被控端保活 + 工具无关 + 自建中转 + 真终端与 agent 感知双视图。**
3. **最硬的两条空白有官方文档背书。** Claude Code Remote Control 文档明确写着：API Key 不支持、`ANTHROPIC_BASE_URL` 指向非 `api.anthropic.com`（v2.1.196 起）不可用、Bedrock/Vertex/Foundry 不可用、本地进程必须常驻并「在 tmux 或 screen 里启动」；而 Win32-OpenSSH #2291（2024-10 开启，至今 Open，无人认领）承认「Windows 没有 tmux 等价物」。**走中转 API 的国内用户 × Windows 被控端**，是被两家官方同时放弃的交集。
4. **用户已把「起任务→走开→手机盯→回来验收」当默认用法**，痛点排序前三是：断线静默失效（#34255 👍107）、等审批无人知（#13024 👍81）、多会话无总览（#30154 👍227）。Windows 是所有方案里问题最密集的被控端。
5. **诚实评估：「手机上继续 Claude Code 会话」这一层已无空白；terminalX 的差异化只有在「多机 + Windows + 工具无关 + 自建」四项同时兑现时才成立**，否则会被 Paseo（同构架构、Apache-2.0、支持 Windows）或 Happier（11 种 agent + ACP + 自建 relay）覆盖。最大威胁不是官方，而是这两个开源项目。

## 1. 三类方案全景图

### 1.1 GUI 远程（像素流）：ToDesk、向日葵、TeamViewer、AnyDesk、网易 UU远程、RustDesk、Parsec、Chrome Remote Desktop、RDP

- **本质**：把整块屏幕编码成视频推给手机。1080p60 桌面视频通常数 Mbps 至 30 Mbps（社区实测，待核实），而一个 AI CLI 会话只需 KB/s 级文本与几十字节的事件。
- **对 AI CLI 场景的四个结构性缺陷**：① 手机上远控画面里的终端字体只有几像素高，免费档 30 FPS + 压缩让 diff 与日志发糊；② 虚拟键盘缺 Esc/Ctrl/Tab/方向键（Chrome Remote Desktop 甚至缺修饰键）；③ 只有「连上/断开」通知，agent 等审批时用户毫无感知；④ RDP 断开即锁屏、机器休眠即断连、无显示器要 dummy plug。
- **商业与信任面**：ToDesk 2024–2025 三次削减免费额度（至每月 200 次/80 小时，再到不公布，待核实）；TeamViewer「商业用途检测」误判；AnyDesk 两年涨价 40–118%（待核实）且 2024 年源码与签名私钥泄露；向日葵 2022 年 RCE；RDP 2025 年多个 RCE。远控已成电诈标配工具，企业与高校发文禁装向日葵/ToDesk。
- **趋势**：厂商在向终端靠拢——RustDesk 1.4.1 起有 Terminal 模式、1.4.5 移动端加浮动快捷键（版本日期各来源不一致，待核实）；网易 UU远程 2026-04/05 上线零配置终端与端口映射。RustDesk 那一档仍是「单机 shell」；**UU远程 已经走出这一档**——终端支持会话分离与重新接入，另有 `uuyc-cli` 与端口映射，缺的是 AI 事件通知、多机聚合、Web 入口与可自建（2026-09-03 补充核实，见 [research/07](research/07-UU远程终端实现分析.md)）。

### 1.2 终端级远程（字节流）：SSH + tmux/Zellij/psmux、mosh/ET、Tailscale/Cloudflare/ngrok/frp、ttyd/sshx/upterm、Termius/Blink、VS Code Tunnels

- **五层拆解**：网络层（穿透）→ 传输层（断线容忍）→ 会话层（保活）→ 呈现层（浏览器/手机）→ Agent 层（感知）。绝大多数工具只做一层，用户要自己拼装。
- **Windows 被控端是断裂点**：Win32-OpenSSH #2291 承认没有 tmux 等价物；sshd 断线后子进程有时被 job object 杀掉（#1418/#1642）、有时变孤儿（#1751）；mosh、Eternal Terminal、Tailscale SSH 都没有 Windows 服务端；ConPTY 兼容裂缝导致 Claude Code 2.1.30 在 Termius→Windows OpenSSH→PowerShell 链路下键盘失效（#22948），Codex Desktop Remote SSH 向 PowerShell 发送 POSIX 引导脚本直接 ParserError（codex #22757，2026-05，Open）。原生替代品 psmux 与 Zellij 0.44（2026-03-23 原生 Windows）刚出现；Zellij 0.45（2026-08-20）已有移动端触屏 Web UI 与桌面通知合并——它是最接近 terminalX 的现成参照，但仍单机、无账号、需自理 TLS 与穿透。
- **网络层在国内不稳**：Tailscale 无官方 DERP、Cloudflare 浏览器 SSH 短期证书在 Windows 有 issue、ngrok 2026-02 收紧免费额度（待核实）、frp 需 VPS 手工运维。
- **移动端物理限制**：iOS 后台 20–30 秒挂起断连；SSH 客户端只是终端仿真器，不知道 agent 何时在等审批（Termius 官方博客自认「缺少 agent 感知」）；手机 SSH 会丢 CJK 输入（#91205）。

### 1.3 AI 代理远程控制（事件流）：官方遥控 + 第三方伴侣 + IM 桥接

| 形态 | 代表 | 共同特征 | 共同短板 |
|---|---|---|---|
| 官方本地会话遥控 | Claude Code Remote Control、Codex 手机遥控、Cursor、Kimi、MiniMax Code、ZCODE | CLI 出站轮询厂商云 + 自家 App | 单厂商；绑订阅账号；中转 API 即失效；一进程一会话；进程须常驻；只有聊天 UI 无终端 |
| 第三方手机/Web 伴侣 | Happy、Happier、Paseo、Omnara、CC Pocket、MobileCLI、claudecodeui、VibeTunnel、VibeAround | 本机 daemon + relay/隧道 + App/浏览器 | 单 daemon 视角无 fleet；Windows 支持参差（VibeTunnel 明确不支持）；小团队维护 |
| IM 机器人桥接 | cc-connect（13 个 IM、10+ agent、多数无需公网 IP）、Claude Channels、OpenClaw、claude-client | 把 CLI 接到飞书/微信/Telegram | 只有对话没终端；消息编辑上限与会话超时；CLI 与桥接都要常驻终端（Windows 无 tmux） |

已退出者：Terragon（云端多 agent 编排）2026-01 关停；Omnara 转型为 managed agents 平台。信号：纯云端编排被官方挤压，**本地遥控**是开源社区最活跃的区域。

## 3. 三个用户画像

### 画像 A：「盯盘的独立开发者」——小周，31 岁，一人公司 / 副业 SaaS
- **设备**：家里一台 Windows 11 台式机（RTX 显卡，常年开机，装了 Claude Code、Codex、Kimi CLI），一部 Android 手机，偶尔 iPad。
- **API 配置**：Claude Code 走国内中转站 API Key（`ANTHROPIC_BASE_URL` 指向中转），Codex 用 Plus 账号，Kimi 用 Coding Plan——**官方 Remote Control 对他直接不可用**（文档：API Key 不支持、非官方 base URL 禁用）。

## 4. AI 时代的新变化：从写代码到监工多个 agent

2025–2026 年的开发者工作循环已变成 codex #37967 描述的样子：「keyboard + terminal on the workstation; phone as a second screen for status + decisions while away from the desk」。这对远程工具提出了六项以前不存在的需求：

1. **「远程」的对象从屏幕/终端变成「会话状态」。** 用户要的不是看到桌面，而是回答「谁在跑、谁在等我、谁完成了、谁挂了」。Anthropic 用 Agent View 把这写进了产品（Working / Needs input / Idle / Completed / Failed / Stopped，Needs input 置顶），但只在单机、只管 Claude。远程工具必须以「会话」而非「设备」或「屏幕」为一等对象。
2. **通知从「连接事件」变成「决策事件」。** 传统远控只有连上/断开；AI 时代的关键事件是 `permission.requested`、`question.asked`、`turn.completed`、`session.idle`、`error`。调研 04 证实这些事件已有可编程通道：Claude `PermissionRequest`/`Notification` hook（含 `http` 类型）与 `--permission-prompt-tool`、Codex `app-server` JSON-RPC 审批与 `notify`、OpenCode `permission.asked` SSE + REST 回复，以及覆盖 9 个 CLI 的 ACP。远程工具不必再靠正则猜「(y/n)」。
3. **决策必须能远程完成且不过期。** 审批是一等对象：跨端可见、持久化、继承本地权限模式、可批量、附带工具名/命令/目录/diff。反例已经很多：Claude RC 转发对话框 5 分钟过期、远程端无视 `--dangerously-skip-permissions`（#29214）、Happy 审批超时断连（#1208）。
4. **并行是默认形态，会话数量级从 1 变成 10–20。** 官方文档给出 `claude --worktree` 并行、Remote Control server 模式 `--spawn worktree`、Grok Build 最多 8 个子代理跑 worktree；#77252 一台 Windows 20 个定时会话；#33979「468 个会话导致启动冻结」。会话的命名、分组、清理孤儿进程、按 worktree 组织成为基础设施需求，而非高级功能。
5. **被控端必须是「守护进程」而非「一个终端窗口」。** 长任务要跨越断网、锁屏、休眠、PC 重启；官方方案要求「Local process must keep running」并建议 tmux，Windows 上没有答案。远程工具要自己承担 tmux 的角色：持有 PTY、环形缓冲、序号补差、多端附着、崩溃重启、远程解卡。
6. **成本与额度成为运行时状态。** 「十个 agent 并行额度消耗约十倍」（官方 Agent View 文档），#16157（👍693）与 #35744（👍97）说明用户要的是「看得见谁在烧」和「额度重置后自动续跑」。远程工具需要把 token/额度作为会话属性展示——这在以前的远程工具里根本不存在。

两个环境变化放大了上述需求：**遥控能力已成为 CLI 选型因素**（codex #9200 190 票，多人称因 Remote Control 留在 Claude）；**每家厂商都在复制同一模式但只管自家工具**，而用户通常同时有 2–3 个 CLI，「工具无关」已成社区共识（Paseo 5 种 agent、cc-connect 10+ agent）。

## 5. 市场空白（诚实评估）

### 5.1 已被填满、不应再做的位置
- **「手机上继续我的 Claude Code 会话」**：官方 Remote Control（随订阅免费、2026-08 起可从手机新建会话、有 Trusted Devices）+ Happy + Paseo 已把体验做得不错。terminalX 在这一层没有胜算，也不必竞争。
- **「把 Claude Code 接进飞书/微信」**：cc-connect（15.3k★，13 个 IM、多数无需公网 IP）、OpenClaw、飞书官方 bridge 已商品化。terminalX 的 IM 只应做「告警 + 一键回到控制台」通道。
- **「云端并行跑很多 agent 出 PR」**：Claude Code on the web / Codex cloud / Cursor Cloud 内置，Terragon 已关停。

### 5.2 「可能根本不存在空白」的证据（必须正视）
1. **Paseo 与 terminalX 架构同构**：本机 daemon + 可选 E2E relay + Docker 自托管 + 桌面/手机/Web/CLI 多端 + 5 种 agent + 明确支持 Windows，Apache-2.0，15.9k★。从架构图看，terminalX 第一阶段几乎是 Paseo 的子集。
2. **Happier 已覆盖「多工具 + 自建 relay + 跨机 handoff + 企业认证（OAuth/OIDC/mTLS）」**。
3. **官方在快速补短板**：Claude server 模式单机 32 并发、跨会话消息、2026-08 设备卡片与可靠性升级；Codex 2026-05-29 补 Windows 主机、app-server 已是可远程的 WebSocket 服务。「单厂商多会话」会越做越好。
4. **Zellij 0.44/0.45 补上了 Windows 原生多路复用 + Web client + 触屏 UI**，psmux 补上了 Windows tmux。「Windows 没有 tmux」这条空白正在被开源填补。
5. **需求密度集中在 Claude Code 生态**：高 👍 issue 几乎都在 anthropics/claude-code，Codex/Gemini/Kimi 的远程需求小一个数量级。「多工具」的付费意愿待验证。
6. **国内 IM 遥控已有事实标准**（cc-connect），国内开发者习惯用微信/飞书而非专用 App；Web 页面能否成为国内用户第一入口，没有证据。

### 5.3 仍然成立的空白（有一手证据）
| 空白 | 证据 | 谁最接近 | 差距 |
|---|---|---|---|
| **多机 fleet 控制台**：机器为一级实体、会话为二级、一屏看在线/离线/等审批/出错/用量 | 官方多机只是带主机名前缀的会话列表；Agent View「Sessions are local」；#30154/#2112/#33979 | Happy（多机会话列表）、Happier（跨机 handoff） | 均无机器维度的状态、用量、告警聚合 |
| **Windows 服务级被控端**：ConPTY 托管、崩溃重启、睡眠/重启处理、远程解卡、按会话选 shell | Win32-OpenSSH #2291 Open 无人认领；#51267/#86084/#77252/#91592 全是 Windows；codex #22757/#34584 | psmux/Zellij（多路复用层）、Paseo（daemon） | 没有人把「保活 + 解卡 + shell 选择 + 电源处理」做成面向 AI CLI 的产品化服务 |
| **中转 API 友好 + 国内可达自建中转** | 官方文档硬限制（API Key、`ANTHROPIC_BASE_URL`、Bedrock、ZDR）；#76653；Happy relay 境外超时 #105 | Paseo/Happier 自建 relay | 无国内节点、无一键部署、无中文 IM 通道整合 |
| **真终端 + agent 感知双视图** | 官方只有聊天（GeekNews/V2EX 抱怨，待核实）；VibeTunnel 只有终端且无 Windows | VibeAround（单机雏形） | 无多机、无服务化、单人维护 |
| **团队/合规语境**：谁能控哪台机、审批分级、审计、只读观察者、E2E fail-closed | ZDR 组织不能用官方；#88094/#88875；opencode 裸奔；RustDesk 降级明文 | Happier 企业认证、Happy E2E、Zellij 只读 token | 无人把这些组合成默认安全模型 |

### 5.4 结论与成立条件
- terminalX 的差异化**成立，但窄**：它不是「又一个手机遥控 Claude Code 的 App」，而是「跨机器、跨工具、可自建、Windows 原生的 agent 控制塔」。
- **成立的前提是四项同时兑现**：多机 fleet 视图、Windows 服务级被控端、工具无关（P0 Claude Code + Codex，MiniMax 建模为供应商预设）、自建中转（国内可达、E2E、只出站）。只做其中一两项，就会被 Paseo/Happier 覆盖。
- **必须正面回答「为什么不用 Paseo」**：答案只能是 fleet 视角 + Windows 服务化与远程解卡 + 真终端 + 中文 IM 与国内网络。这四点要在第一阶段的原型里就可见，而不是路线图里。
- **第一阶段范围要克制**：一个 Web 页面控制一台 Windows 上的多个终端/AI CLI 会话，断线不丢会话、手机可用、Claude Code 与 Codex 的「等你确认」能推送并一键回复。跨机器接续、P2P、录制回放放二期。
- **失败信号**：若 Paseo 加上机器维度面板与 Windows 服务化，或 Anthropic 放开自定义 `ANTHROPIC_BASE_URL` 的 Remote Control（#76653 已有请求），两条最硬空白会同时收窄，届时只剩「工具无关 + 国内可达」。
