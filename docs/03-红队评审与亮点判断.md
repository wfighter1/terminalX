# terminalX 红队评审与亮点判断

> 日期：2026-09-03
> 流程：三份独立产品方案（A · AI 原生监工台 / B · 务实 MVP / C · 安全自建与团队）→ 三位评审按不同视角打分 → 三位红队分别从「官方产品负责人」「已有 Tailscale + tmux 或 Happy 的挑剔用户」「技术合伙人」视角逐条反驳 → 完整性审查找出文档间矛盾。本文汇总结论；最终裁决已落到 `docs/02-产品设计.md`。
> 说明：评审与红队均为本次调研流程中由 AI 按不同视角独立生成的意见，每一位都打开一手来源核实后再下结论，但不是外部真人访谈；一手用户验证见设计文档 §18。文中「画像 A」指「Windows 台式机 + 中转站 Key + 手机」的独立开发者，「画像 C」指有合规要求的团队用户，定义见设计文档 §3。

## 1. 评审团打分

| 视角 | 方案 A · AI 原生监工台 | 方案 B · 务实 MVP | 方案 C · 安全自建与团队 | 胜者 |
|---|---|---|---|---|
| 用户价值与痛点契合 | 6.8 | **7.5** | 5.2 | B |
| 可行性与聚焦（一人 4–6 周） | 5.4 | **8.3** | 6.2 | B |
| 差异化与防御性（12 个月后） | 5.8 | **7.6** | 6.6 | B |

**一致结论：** 以方案 B 的范围纪律与验收体系为骨架，嫁接 A 的感知层与审批对象设计、C 的安全默认值与供应商预设。

- **A** 的产品命题最贴近 AI 时代监工需求（收件箱为一等对象、Unknown 状态、远程 ≤ 本地、夜报），但两大亮点的差异化前提经核实动摇（Happier 已有跨机跨工具收件箱；API Key 没有额度重置可等），MVP 明显堆砌（一人 12–16 周）。
- **B** 是唯一「每个亮点 = 画像 A 的一条 Top3 痛点 = 一条可复现验收」的方案，其自报的 4–6 周在三份方案里最可信；扣分在护城河最薄、Codex 与成本展示过度保守、缺供应商预设。注意：打分针对的是方案自报周期；红队核算审批通道重设计与手机输入层改造后，最终排期定为 8–10 周（见 §3 末行与设计文档 §14）。
- **C** 安全叙事扎实、诚实度最高，但四个亮点对应痛点表第 11、12 位，核心场景写的是第一阶段不交付的画像 C；它是一份优秀的三期路线图。

## 2. 红队总判断

| 视角 | has_real_edge | 置信度 | 一句话 |

## 4. 存活的亮点

1. **结构性**：中转 Key / API Key / Bedrock / 网关 / ZDR 用户被官方全部远程面排除（feature-availability 页：require signing in with a claude.ai account）；v2.1.196 是收紧。
2. **结构性 + 时效性**：Windows 上工具无关的会话宿主 + 崩溃自启 + 远程解卡：Codex CLI Windows daemon 至今不可用（#42507 2026-09-03 Open）；Claude RC Win11 静默挂起只有本地 Esc 能救（#51267 Open）；官方聊天 UI 结构上发不出 Esc / Ctrl-C。窗口约 6–12 个月。
3. **地理性**：国内可达的一条命令自建中转 + 中文 IM 告警 + 「远程终端」命名与数据流向图。
4. **执行质量**：真终端 + agent 感知双视图；免包装器附着到用户自起的会话；全局状态条 + Unknown 状态 + 置信度；三信号分离。
5. **产品规则**：远程 ≤ 本地；审批去重与本机处理自动关闭；供应商预设在被控端注入不经中转；statusLine 两个数字。
6. **交付纪律**：方案 B 的可脚本化验收（`seq 1 20000` 逐字节、≤60 秒自启、无 `0.0.0.0` 监听、中转日志不含内容）与「每砍一项写回归路径」。
